# Bear Code 技术亮点

本文档梳理 Bear Code 的技术亮点。重点不是罗列 CLI 功能，而是说明 Bear Code 作为一个自研 Agentic Harness，如何把模型推理、工具调用、权限控制、会话记忆折叠、Skills 自进化、MCP、子 Agent 和评测链路组织成一个可运行、可沉淀、可审计的 Coding Agent Runtime。

## 1. 项目定位

Bear Code 是一个本地命令行 Coding Agent Runtime。它的核心不是“套一层大模型 API”，而是实现了一套 Harness：

```text
用户输入
  -> 构建 system prompt、Memory、Skills、MCP 工具上下文
  -> 调用 OpenAI / Anthropic 兼容模型
  -> 解析 tool call
  -> 权限检查
  -> 执行内置工具 / Skills / MCP 工具 / 子 Agent
  -> 工具结果回写模型
  -> 必要时折叠会话记忆
  -> 保存 session、触发 Skills 自进化和评测审计
```

因此，项目亮点集中在三个层面：

- **运行时编排**：统一管理模型、工具、权限、上下文和持久化。
- **长程任务能力**：通过自主会话记忆折叠和分层 Memory / Skills，降低上下文膨胀对任务推进的影响。
- **自进化能力**：先判断反馈是否能由 Skill 修复，再把可信缺口沉淀为 Skills；候选还要经过同样本回归检查和 champion gate。

## 2. 技术亮点总览

| 亮点 | 核心价值 | 主要代码 |
| --- | --- | --- |
| Agentic Harness 运行时 | 统一编排模型推理、工具调用、权限检查、结果回写和会话保存 | `agents/agent.py`、`agents/main.py` |
| 自主会话记忆折叠 | 在长程任务中将历史交互折叠为结构化 session state，保留任务进度、当前目标和工具经验 | `agents/session_memory.py`、`agents/agent.py`、`agents/session.py` |

## 3. Agentic Harness 运行时

### 解决的问题

普通聊天式工具只完成“用户输入 -> 模型回复”。但 Coding Agent 需要持续处理模型请求、工具调用、权限判断、工具结果、上下文压缩、会话保存和后台沉淀。Bear Code 将这些能力收敛到 `Agent` 运行时中，形成完整的推理、行动、观察、继续推理闭环。

### 实现思路

核心入口是 `Agent.chat()`：

```text
初始化 MCP
  -> 弹出上一轮 pending window
  -> 检索并注入相关 Skills
  -> 根据协议进入 OpenAI 或 Anthropic 主循环
  -> 模型产生 tool call
  -> Runtime 统一执行权限检查和工具分发
  -> 收集 assistant 输出
  -> 后台触发 Skills usage tracking 和 online evolution
  -> 保存 session
```

工具调用统一从 `_execute_tool_call()` 分发：

- `compact_context`：触发自主会话记忆折叠。
- `skill`：调用已注册 Skill，支持 inline 和 fork。
- `agent`：启动子 Agent。
- `mcp__server__tool`：路由到 MCP server。
- 其他工具：交给 `agents/tools.py` 执行。

### 技术价值

- **统一控制权**：模型只提出 tool call，本地动作由 Runtime 执行。
- **协议可替换**：OpenAI-compatible 与 Anthropic-compatible 复用同一套工具、Memory、Skills 和权限体系。
- **能力可扩展**：内置工具、MCP 工具、Skills、子 Agent 都能纳入统一调度。
- **状态可保存**：每轮结束自动保存 session，并为后续自进化提供对话证据。

## 4. 自主会话记忆折叠

### 解决的问题

长程任务中，原始对话、工具结果、失败尝试和中间分析会持续堆积，导致上下文变长、关键信息被淹没、失败路径影响后续推理。Bear Code 借鉴 DeepAgent 的 memory folding 思路，将它实现为“自主会话记忆折叠”：它不是简单裁剪历史，而是把会话重组为可继续执行的结构化状态。

### 实现思路

折叠 schema 在 `agents/session_memory.py` 中定义，包含三层：

```text
episode_memory
  -> 任务描述、关键事件、当前进度

working_memory
  -> 当前子目标、阻塞点、下一步动作

tool_memory
  -> 已用工具、有效参数、常见错误、返回模式、工具经验
```

触发方式有两类：

- **模型主动触发**：模型可以调用 `compact_context` 工具，适用于上下文变长、工具反复失败、策略需要重启等场景。
- **系统阈值兜底**：当输入 token 接近上下文阈值时，Runtime 自动调用折叠流程。

折叠流程大致为：

```text
收集当前会话 transcript
  -> 调用 side query 生成三层结构化 JSON
  -> 解析失败时使用 fallback folded memory
  -> 将原始历史替换为 <session-folded-memory>
  -> 折叠记录落盘到 .bear/sessions/
  -> Agent 从折叠后的状态继续执行
```

### 代码落点

- `agents/session_memory.py`：定义三层 session memory schema、transcript 构造、JSON 解析和 fallback。
- `agents/tools.py`：暴露 `compact_context` 工具。
- `agents/agent.py`：实现 `_compact_conversation()`、`_execute_compact_context_tool()`、自动阈值触发和折叠后消息重建。
- `agents/session.py`：将折叠记录保存到当前项目 `.bear/sessions/`。

### 技术价值

自主会话记忆折叠的价值不只是减少 token，而是支持长程任务中的状态重组：

- 保留任务进度、当前子目标、阻塞点和下一步动作。
- 保留工具调用经验，避免重复走失败路径。
- 在策略变化或多次失败后，为 Agent 提供“重新整理局面”的机会。
- 让长对话不依赖完整原始历史，也能从结构化状态继续推进。

需要注意的是，当前 `--resume` 主要恢复原始模型消息历史；折叠记录会作为审计和最新折叠状态保存到 `.bear/sessions/`，不是一个独立的跨进程长期记忆系统。

## 5. Memory + Skills 分层长期上下文

### 解决的问题

Agent 需要记住两类不同信息：

- **Memory**：项目事实、用户偏好、历史决策、参考资料。
- **Skills**：可复用的方法、工作流、格式要求和任务策略。

如果把它们混在同一段 prompt 中，会导致上下文污染：项目事实可能被当成通用方法，任务流程也可能被误认为当前项目状态。

### 实现思路

Bear Code 将 Memory 和 Skills 分层：

- `agents/memory.py` 负责文件型长期记忆。它按当前项目隔离 memory 目录，使用 Markdown + frontmatter 保存条目，并通过 side query 选择相关 memory 注入当前会话。
- `agents/skills.py` 负责 Skills 加载、检索和调用。它扫描用户级 `~/.bear/skills/` 和项目级 `.bear/skills/`，解析 `SKILL.md`，并使用 BM25-lite 检索相关 Skills。

Skills 支持两种执行模式：

- **inline**：将 Skill 指令注入当前上下文，由主 Agent 继续执行。
- **fork**：启动隔离子 Agent 执行 Skill，适合需要独立上下文的任务。

### 技术价值

- Memory 解决“这件事之前发生过什么”。
- Skills 解决“这类事以后应该怎么做”。
- 两者分层后，长期上下文更可控，也更适合长程任务和重复任务。

## 6. Skills 自进化

### 解决的问题

很多用户反馈不是一次性的，例如“以后写简历不要写成 STAR 标题”“评测文档只保留 Pass@1”“这类内容要先给结论”。如果这些反馈只留在当前会话里，下次仍然需要用户重复说明。

Bear Code 的 Skills 自进化链路就是把稳定反馈沉淀成可复用 `SKILL.md`。

### 实现思路

自进化流程以 pending window 为核心：

```text
本轮用户请求 + assistant 回复
  -> 保存 pending window
下一轮用户输入
  -> 作为上一轮反馈证据合并进 window
  -> Attributor 先判断 skill_gap / capability_limit / evaluation_noise
  -> 只有 skill_gap 由 Extractor 抽取最多一个可复用 Skill 候选
  -> Maintainer 结合已有 Skills 做相似检索
  -> 决策 add / merge / discard
  -> 把 add / merge 写成隔离 proposal，active SKILL.md 保持不变
  -> /skill-eval 通过双锚点门禁后写 champion
  -> /skill-promote 显式发布到 active SKILL.md
```

Extractor 的约束包括：

- 用户消息是主要证据，assistant 只能作为上下文。
- 只抽取可复用的工作流、输出策略、实现偏好或纠正。
- 不抽取一次性任务内容、隐私、URL、账号 ID、精确日期和临时参数。

Maintainer 的约束包括：

- 已有相同能力时优先 merge，不盲目新增。
- 重复且无增量价值时 discard。
- merge 时保留已有有用指导，只加入稳定新规则。

### 代码落点

- `agents/online_skill_evolution.py`：Extractor、Maintainer、online ingest 主流程。
- `agents/skill_evolution.py`：`SKILL.md` 创建、演化、版本 bump、history 快照、provenance 和 usage 记录。
- `agents/agent.py`：在每轮对话后调度 usage tracking 和 online skill evolution。

### 技术价值

- 把用户反馈从“当前上下文提醒”变成“可复用能力”。
- 通过 add / merge / discard 控制 Skill 膨胀。
- 通过 provenance、history 和 usage stats 保证自进化过程可追踪。

### 实现细节一：Skill 信息分三层进入模型

Bear Code 没有在每次请求中直接塞入所有完整 `SKILL.md`。它将“知道有哪些 Skill”和“真正加载某个 Skill”拆成三层，以控制上下文成本。

#### 第一层：System Prompt 中的轻量 Skill 清单

`agents/prompt.py::build_system_prompt()` 调用 `agents/skills.py::build_skill_descriptions()`，把已发现 Skill 的以下信息写入 System Prompt：

- 名称。
- 描述。
- `when_to_use`。
- 是否支持用户通过 `/<skill-name>` 调用。

这里不包含完整正文。它只让模型知道当前有哪些能力，以及在什么条件下应该调用 `skill` 工具。

#### 第二层：针对当前请求的相关 Skill 摘要

每次 `Agent.chat()` 开始时，`_augment_user_message_with_skill_context()` 使用当前原始请求进行 BM25-lite 检索，最多选择三个候选。检索文本由名称、描述、触发条件和部分正文组成，但实际注入模型的内容仍然只是摘要：

```text
用户原始请求

<retrieved_skills>
1. skill-name (score=0.820, source=project): description
   When to use: ...
</retrieved_skills>
```

这段文本直接拼接在当前 `user_message` 后面，因此：

- OpenAI-compatible 路径最终以 `role=user` 消息发送。
- Anthropic-compatible 路径最终放入 `messages` 的 user content。
- `top_ref` 和 `all_hits` 不发送给模型，而是保存在 Runtime 中，用于后续身份关联和 usage tracking。
- 没有命中时，模型收到的 user content 就是原始请求。

#### 第三层：通过 `skill` tool call 加载完整正文

模型判断某个 Skill 确实适用后，返回标准工具调用：

```json
{
  "name": "skill",
  "arguments": {
    "skill_name": "example-skill",
    "args": "当前任务参数"
  }
}
```

Runtime 的执行链是：

```text
模型产生 skill tool call
  -> Agent._execute_tool_call()
  -> Agent._execute_skill_tool()
  -> skills.execute_skill()
  -> 按名称找到 SkillDefinition
  -> 展开 $ARGUMENTS 和 ${CLAUDE_SKILL_DIR}
```

之后根据 Skill 的 `context` 分成两种执行方式：

- **inline**：完整正文作为 `tool_result` / `role=tool` 返回主模型，下一次模型请求才真正看到完整 Skill 并继续执行。
- **fork**：完整正文作为子 Agent 的 `custom_system_prompt`，`allowed-tools` 用于缩小子 Agent 工具范围；主模型最终只接收子 Agent 的执行结果。

因此，“自动检索到 Skill”不等于“已经调用 Skill”，而“调用 Skill”本身是一次正常的 tool call。用户直接输入 `/<skill-name>` 是例外：inline Skill 会由 CLI 直接展开成一次 Agent 输入，fork Skill 仍通过 `skill` 工具进入隔离执行路径。

### 实现细节二：自进化使用跨轮反馈窗口

自进化不会在同一轮回答结束后立即把模型自己的做法写成 Skill，而是等待下一条用户消息验证上一轮结果。

```text
第 N 轮开始
  -> 取出第 N-1 轮 pending window
  -> 将第 N 轮用户消息作为对上一轮的反馈补入窗口

第 N 轮主回答结束
  -> 后台记录 retrieved / surfaced / invoked，并评估 relevant / inferred_used
  -> 后台演化已经补齐反馈的第 N-1 轮窗口
  -> 将第 N 轮请求和回答保存为新的 pending window
```

第一轮没有上一轮 pending window，因此只会保存证据，不会产生跨轮演化。第二轮用户可能给出确认、否定或修正，例如“这样可以”“不要使用这种格式”“以后先给结论”，这些消息会成为 Extractor 的主要证据。

窗口中保留：

- 最近的 user / assistant 对话文本，不包含 tool block。
- 上一轮原始用户请求和最终 assistant 文本。
- 本轮最高分 Skill 的紧凑引用，用于判断是在改进已有 Skill 还是产生新能力。
- session id。

Runtime 注入的 `<retrieved_skills>` 会在抽取近期对话时被移除，避免系统自己的检索提示被误当成用户反馈学习。

### 实现细节三：Attributor / Extractor 与 Maintainer 分离

`agents/online_skill_evolution.py` 是自进化决策层，内部使用两次职责不同的 side query。

#### Attributor + Extractor

`analyze_online_feedback()` 在一次请求中先判断失败能否通过修改 Skill 修复，再从“任务、回答、下一轮反馈”中最多抽取一个结构化候选：

```text
skill_gap：缺少稳定工作流、输出约束或实现偏好，修改 Skill 可以解决
capability_limit：缺工具、权限、网络、沙箱、运行时或模型能力，修改 Skill 无效
evaluation_noise：没有明确失败、反馈矛盾、证据不足或只是切换话题
```

只有 `skill_gap` 可以产生候选：

```text
name / description / when_to_use / instructions / evidence / tags
```

主要约束：

- user turn 是主要证据，assistant turn 只提供上下文。
- 只沉淀跨相似任务仍然成立的工作流、输出策略、偏好或纠正。
- 不保存秘密、账号、URL、精确日期、一次性 payload 和临时项目事实。
- `capability_limit` 和 `evaluation_noise` 强制返回空候选，并把原因写入 provenance。

#### Maintainer

`maintain_online_skill_candidate()` 将候选与现有 Skill 集合比较，再决定：

- `add`：没有同类能力，新增一个 Skill。
- `merge`：已有同类能力，把稳定增量合并进去。
- `discard`：重复、证据不足或没有长期价值。

LLM 决策之外还有确定性保护：

- 名称、描述或触发条件命中同一身份时强制 merge。
- 候选与已有 Skill 的相似分数达到 `0.55` 时，避免重复 add，改为 merge 到最高分结果。
- 非法或缺失 action 默认 discard。
- merge 目标为空且无法从引用恢复时拒绝写入。

这种拆分让 Attributor / Extractor 只回答“问题是否可修、学到了什么”，Maintainer 只回答“如何维护能力集合”，避免用 prompt 伪修复工具和环境问题。

### 实现细节四：candidate-first 与后台任务隔离

Skill usage tracking 和 online evolution 都在主回答完成后通过 `asyncio.create_task()` 调度，主回复不会等待辅助 LLM 请求完成。Runtime 保存任务集合，并在 CLI 退出前通过 `drain_background_skill_tasks()` 收尾。

自动进化由 `BEAR_AUTO_SKILL_EVOLUTION` 控制，默认开启；目标范围由 `BEAR_AUTO_SKILL_TARGET` 控制。后台只把候选写入项目隔离的 `.bear/skill-evolution/proposals/`，不会改变 Runtime 正在加载的 active Skill。

生效边界如下：

- 普通后台反馈和 `/extract_now`：只生成 proposal。
- `/skill-eval`：隔离试跑并更新 proposal 的 `evaluated / champion` 状态，不覆盖 active。
- `/skill-promote <skill>`：用户显式发布已过门禁的 champion，才会 create / evolve active Skill。
- `/skill-create`、`/skill-evolve`：保留为用户显式的直接维护命令。
- `plan`：不调度在线演化，也不更新 usage 统计。

因此，`skill_gap` 能触发真实演化，但“发现缺口、证明候选、发布生效”是三个不同阶段。

### 实现细节五：usage tracking 与真实调用审计分离

每轮回答后，`_run_skill_usage_tracking()` 会把原始请求、最终回答和本轮不可变 `skill_trace` 快照交给一个隔离的裁判 side query。裁判为每个候选输出：

- `retrieved`：Runtime 已知事实，表示该候选确实被检索到。
- `surfaced`：Runtime 已知事实，表示该候选摘要确实注入了本轮模型上下文。
- `invoked`：Runtime 已知事实，表示完整 Skill Prompt 已成功解析并展开。
- `relevant`：候选是否适合当前用户请求。
- `inferred_used`：最终回答是否体现该 Skill 的独特流程或策略。
- `reason`：简短判断理由。

这里的 `inferred_used` 是对最终回答行为的语义推断，不是对 `skill` tool call 的直接审计。真实的显式 Skill 调用由 `record_skill_invocation()` 单独写入 `usage.jsonl`，并确定性更新 `invoked` 统计。两种信号刻意分开：

```text
invoked：Runtime 是否确定执行过 skill 工具
inferred_used：最终回答是否表现出采用了该 Skill
```

如果没有可用 side query，`relevant` 和 `inferred_used` 都保守记为 False；系统不再根据回答是否出现 Skill 名称猜测使用情况。裁判失败属于回答后的尽力而为任务，不影响已经生成的主回复。

### 实现细节六：累计统计、归档与缓存刷新

`agents/skill_evolution.py::record_skill_usage_judgments()` 按 Skill 累计：

```text
retrieved / surfaced / relevant / invoked / inferred_used
last_retrieved / last_surfaced / last_relevant / last_invoked / last_inferred_used
last_reason / last_score
source / skill_dir
```

默认情况下，一个用户级 Skill 被展示至少 40 次且真实调用仍不超过 0 次，会被视为长期无效。`inferred_used` 只用于诊断，不参与归档。项目级 Skill 默认不自动归档，只有显式启用 `BEAR_SKILL_PRUNE_PROJECT` 才参与；阈值可通过以下变量调整：

- `BEAR_SKILL_USAGE_PRUNE_MIN_SURFACED`
- `BEAR_SKILL_USAGE_PRUNE_MAX_INVOKED`

归档使用目录移动而不是删除：

```text
原 Skill 目录
  -> .bear/skill-evolution/pruned/<skill-name>-<timestamp>/
```

只有显式 publish、手动 add / merge 或 prune 成功后才会清空 Skill 发现缓存并重建 System Prompt；proposal 和 champion 都不会改变当前能力清单。

### 实现细节七：模块边界和审计产物

自进化并不只涉及 `skills.py` 和 `skill_evolution.py`，而是由多个职责明确的模块协作：

| 模块 | 边界 |
| --- | --- |
| `agents/agent.py` | 跨轮窗口、后台调度、side query、proposal 事件 |
| `agents/online_skill_evolution.py` | Extractor、Maintainer、add / merge / discard 决策、usage judge |
| `agents/skills.py` | Skill 发现、检索、调用以及创建/演化/统计的业务门面 |
| `agents/skill_evolution.py` | proposal 生命周期、确定性持久化、版本、history、provenance、usage stats、prune |
| `agents/online_skill_eval.py` | replay、规则、候选试跑、champion 记录和显式 publish |
| `agents/prompt.py` | 把最新 Skill 清单重新写入 System Prompt |
| `agents/main.py` | `/extract_now`、`/skill-proposals`、`/skill-eval`、`/skill-promote` 等人工入口 |
| `agents/tools.py` | `skill`、`skill_create`、`skill_evolve` 工具 schema、权限和路由 |

主要落盘产物包括：

| 路径 | 内容 |
| --- | --- |
| `.bear/skills/<name>/SKILL.md` | 项目级 active Skill |
| `~/.bear/skills/<name>/SKILL.md` | 用户级共享 active Skill |
| `.bear/skill-evolution/usage.jsonl` | 显式调用、创建、演化、归档等使用事件 |
| `.bear/skill-evolution/online_provenance.jsonl` | 每次在线抽取和维护的原始审计事件 |
| `.bear/skill-evolution/online_skill_provenance.json` | 按 lineage 聚合的 provenance 索引 |
| `.bear/skill-evolution/skill_usage_stats.json` | retrieved / surfaced / relevant / invoked / inferred_used 累计统计 |
| `.bear/skill-evolution/proposals.json` | proposal 状态索引 |
| `.bear/skill-evolution/proposals/<id>/` | 隔离候选的 JSON 与可审阅 `SKILL.md` |
| `.bear/skill-evolution/history/` | merge 前的版本快照和演化历史 |
| `.bear/skill-evolution/pruned/` | 长期无效但仍可恢复的归档 Skill |

这条链路形成了完整闭环：真实反馈提供证据，Attributor 隔离不可修复信号，Extractor 提炼方法，Maintainer 生成隔离 proposal，评测层通过 replay、逐样本回归和 champion 验证质量，最后由显式 publish 改变 active。

## 7. Skills 自进化质量评测

### 解决的问题

自动沉淀 Skill 之后，不能默认它就是正确的。需要回答几个问题：

- 这个 Skill 从哪些真实对话来？
- 它在历史任务中是否真的改善了输出？
- 规则是否可回放、可比较？
- 候选改进是否优于当前版本？
- 哪个版本可以作为当前本地已知的健康版本？

Bear Code 使用在线 Skills 评测链路对这些问题做质量观察。

### 实现思路

评测入口在 `agents/online_skill_eval.py`。核心流程：

```text
读取 online provenance / usage stats / active skills
  -> 按 Skill 聚合 lineage
  -> 从历史对话构造 replay pool
  -> 从 SKILL.md 编译规则
  -> 对历史 latest_assistant 做规则评测
  -> 可选启用 LLM judge
  -> 基于失败规则生成候选版本
  -> 用候选版本重新生成 replay 回复
  -> 在同一 mutate_dev 上比较 current active 与 candidate
  -> 在隔离 promotion_test 上逐样本检查回归
  -> 再与历史 champion 比较
  -> 满足双锚点 gate 时写入 champion 记录
```

当前支持的评测能力包括：

- **replay 样本池**：从真实在线沉淀记录中构造，并固化到 `.bear/skill-evolution/online-eval/datasets/`。
- **规则评测**：根据 Skill 文本编译非空、JSON、表格、引用来源、结论前置、段落限制等程序规则。
- **LLM judge**：在有模型侧调用能力的路径下，用模型判断回复是否满足 Skill 指令。
- **候选版本试跑**：根据失败规则生成 heuristic candidate，也可以生成 LLM candidate，并重新跑 replay。
- **逐样本回归治理**：以 `sample_id + rule_id` 为最小单元，统计 current active 已通过但 candidate 失败的项目；默认不允许回归，任何硬规则回归都会阻断候选。
- **双锚点 champion 记录**：candidate 先对照 current active 保证不回退，再对照历史 champion 保证跨轮收益，满足 gate 后才写入本地产物。

### 边界说明

当前 champion 是本地评测记录和候选产物，不会自动覆盖 active `SKILL.md`。只有 `/skill-promote <skill>` 才发布已过门禁版本。`summary.json` 同时保存 dev 增益、regression rate、hard regressions 和具体回退样本，使“为什么没有晋级”可以审计，而不是只留下一个总分。

## 8. 工具系统、权限控制与 Plan Mode

### 解决的问题

Coding Agent 可以读写文件、执行 Shell、创建 Skill、调用外部工具。如果没有工具边界，风险包括：

- 未读文件就编辑，覆盖用户修改。
- 执行危险命令。
- 在计划阶段提前修改项目。
- 随意创建或演化 Skill，污染长期能力。

### 实现思路

`agents/tools.py` 将工具分为只读、编辑和需要确认的动作：

- 只读工具：`read_file`、`list_files`、`grep_search`、`compact_context`。
- 编辑工具：`write_file`、`edit_file`、`skill_create`、`skill_evolve`。
- Shell 工具：根据命令风险进入确认或拒绝路径。

关键保护包括：

- Plan Mode 下阻断普通写操作和 Shell，只允许围绕计划文件工作。
- 写入新文件、危险命令、Skill 创建和 Skill 演化需要确认。
- 编辑已有文件前必须先 `read_file`，并记录 mtime；如果文件在读取后被外部修改，需要重新读取。

### 技术价值

这部分体现的是 Harness 的控制边界：模型可以提出动作，但是否执行、如何执行、是否需要确认，都由 Runtime 决定。

## 9. MCP 与子 Agent

### MCP 外部工具接入

Bear Code 自己实现了 stdio JSON-RPC MCP Client，而不是把外部工具硬编码进项目。实现路径：

```text
读取 ~/.bear/settings.json、.bear/settings.json、.mcp.json
  -> 启动 MCP server 子进程
  -> initialize
  -> tools/list
  -> 包装为 mcp__server__tool
  -> 模型调用时路由到 tools/call
```

这样可以把浏览器、搜索、数据库、内部系统等外部能力统一接入 Agent 工具层。

### 子 Agent

子 Agent 用于隔离上下文和任务边界。当前内置：

| 类型 | 工具范围 | 适用场景 |
| --- | --- | --- |
| `explore` | 只读工具 | 快速代码搜索、定位实现 |
| `plan` | 只读工具 | 输出结构化实施计划 |
| `general` | 除 `agent` 外的大部分工具 | 独立处理局部任务 |

项目还支持 `.bear/agents/*.md` 自定义子 Agent，并可通过 `allowed-tools` 控制工具范围。

## 11. 简历可提炼的技术亮点

可以将项目技术亮点浓缩为以下几条：

- 自研 Agentic Harness，统一编排模型推理、tool call 解析、权限检查、工具执行、结果回写、会话保存和上下文折叠，支持 OpenAI / Anthropic 双协议、MCP、Plan Mode 和子 Agent。

## 12. 当前实现边界

为了保证表述和代码一致，当前文档对以下边界做明确说明：

- 自主会话记忆折叠是 session 级状态折叠，不等同于完整的跨项目长期记忆系统。
- 折叠产物会保存到项目 `.bear/sessions/`，当前 `--resume` 主要恢复模型消息历史，折叠记录更多承担审计和状态记录作用。
- champion 是评测产物和健康版本记录，不会自动覆盖当前 active Skill；显式 `/skill-promote` 是唯一的在线发布动作。
- LLM judge 和候选版本试跑依赖可用的模型 side query；没有该能力时，评测会退化为程序规则评测。
- GAIA / HLE 结果来自当前 wiki 测评口径，主指标只保留 Pass@1。
