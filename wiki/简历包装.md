## 2.5 自主会话记忆折叠：目的与价值

### 目的

面向代码探索、调试、重构和多工具协作等长程任务，避免原始对话、工具结果和失败尝试持续堆积，导致上下文膨胀、关键信息被淹没或错误路径持续影响后续推理。

### 核心收益

- **降低上下文开销**：将冗长交互历史压缩为结构化 session state，释放上下文空间。
- **保持任务连续性**：保留整体进展、当前子目标、阻塞问题、下一步动作和工具经验，折叠后可以继续执行。
- **减少错误累积**：在重复失败或策略变化时清理噪声，让 Agent 重新审视当前状态并调整方案。
- **提升长程任务稳定性**：相比固定截断或简单摘要，三层 memory schema 能更稳定地保留任务事实、工作状态和工具使用经验。

### 简历表述

> 设计自主会话记忆折叠机制，使 Agent 能在长程任务中主动或按上下文阈值压缩历史交互，保留任务进展、当前工作状态和工具经验，并基于折叠后的结构化 session state 继续推理和执行。

## 5. 30 秒面试讲法

Bear Code 是我用 Python 实现的自进化 Coding Agent Harness。Skills 链路有两个关键设计：第一，下一轮用户反馈先做可修复性归因，缺工具、权限或评测证据的问题不会被错误写成 Skill；第二，候选先在 dev 选优，再在隔离测试集逐样本检查回归，并与历史 champion 比较，平均分提高但已有能力退化的版本不能晋级。

## 6. 1 分钟面试讲法

这个项目主要解决两个问题：第一，怎么把大模型变成能安全执行软件工程任务的本地 Agent；第二，怎么让 Agent 在使用过程中沉淀能力。  

我实现了一个 Python Agentic Harness，负责模型调用、tool call 解析、权限检查、工具执行、结果回写、会话记忆折叠和会话保存。上层支持文件读写、代码搜索、Shell、Plan Mode、OpenAI / Anthropic 双协议、Memory、Skills、MCP 和子 Agent。会话变长、工具反复失败或需要调整策略时，模型可以主动调用 `compact_context`，系统也提供上下文阈值兜底；折叠后保留任务进度、当前目标和工具经验，继续完成长程任务。

项目最核心的亮点是可控的 Skills 自进化。每轮回复结束后保存 pending window，下一轮用户反馈会被合并为证据，并先归因为 `skill_gap`、`capability_limit` 或 `evaluation_noise`；只有第一类可以抽取候选，随后 Maintainer 决定 add / merge / discard，并只写入隔离 proposal。评测阶段从 provenance 构造稳定的 dev/test replay，候选只在 dev 选优，再在 promotion-test 逐 `sample_id + rule_id` 对比 current active，默认零回归、零硬规则回归，最后进入 champion gate；只有显式 `/skill-promote` 才发布 active。

## 7. 2 分钟深度讲法

Bear Code 的底层是一个自研 Agentic Harness。用户输入进入 `Agent.chat()` 后，系统会初始化 MCP、检索相关 Skills、预取 Memory，然后根据配置选择 OpenAI-compatible 或 Anthropic-compatible 模型接口。模型如果返回 tool call，Harness 会先进入统一的权限检查逻辑，再分发到内置工具、Skill、MCP 工具或子 Agent，执行结果会作为 tool result 回写给模型，形成推理、行动、观察、继续推理的闭环。

在这个闭环里，我重点补了自主会话记忆折叠：当上下文变长时，模型可以主动调用 `compact_context`，系统也会在达到阈值时自动折叠，把原始对话压缩成结构化 session state 后继续执行。这样做的价值是，长任务不会因为窗口膨胀而中断，模型还能保留任务进度、工具经验和下一步动作。

我在这个闭环上做了几个扩展：第一是 Plan Mode，复杂任务先只读分析和写计划，审批后再执行；第二是 Memory 和 Skills 分层，Memory 记录事实和偏好，Skills 记录可复用方法；第三是 MCP Client，通过 stdio JSON-RPC 动态接入外部工具；第四是子 Agent，用隔离上下文处理探索、规划和局部任务。

最重要的是 Skills 自进化和在线评测。系统把用户任务、助手回复和下一轮反馈组成 pending window，Attributor 先隔离工具、权限、环境限制和评测噪声，Extractor 只从可修复反馈中抽取规则，Maintainer 再做 add / merge / discard，但结果先进入 proposal 隔离区。随后 `/skill-eval` 从在线日志构造稳定 replay；候选在 mutate-dev 上与 current active 的同批样本比较，在 promotion-test 上逐样本检查回归，再与历史 champion 比较。通过后也只成为 champion，必须由 `/skill-promote` 显式发布。整个决策保存 attribution、proposal 状态、regression rate、hard regressions 和具体失败项，因此不是无约束自改 prompt，也不是只看一个总分。

## 9. 面试高频问题和回答

### Q1：为什么说它是 Harness Agent，而不是普通聊天机器人？

普通聊天机器人主要是用户输入、模型回复。Bear Code 的核心是 Harness：模型只提出 tool call，真正的文件读写、Shell、Skill、MCP 和子 Agent 都由 Runtime 统一做权限检查、执行调度、结果回写和状态保存。也就是说，它有完整的推理、行动、观察、继续推理闭环。

### Q2：自进化 Skills 到底怎么实现？

每轮回复结束后保存 pending window。下一轮输入作为上一轮反馈进入 `online_ingest()`：Attributor / Extractor 联合判断它属于 `skill_gap`、`capability_limit` 还是 `evaluation_noise`，后两类直接停止；只有 `skill_gap` 能产生候选，再由 Maintainer 判断 add、merge 或 discard。add / merge 只生成隔离 proposal，不直接修改 active。proposal 经 `/skill-eval` 晋级 champion 后，还要由 `/skill-promote` 显式发布。所有归因、来源、状态和维护决定都会进入 provenance。

### Q2.1：Skills 评测怎么做？

`/skill-eval` 会读取在线 provenance、usage stats 和 active Skills，按 Skill 形成 lineage，并从历史对话构造 replay pool。评测先从 `SKILL.md` 编译规则，包括非空、JSON、表格、引用来源等程序规则，以及 LLM judge 的 `skill_instruction_alignment`。然后系统评估历史 `latest_assistant` 是否满足规则，并结合 retrieved / surfaced / relevant / invoked 判断 `unobserved`、`incubating`、`watch` 或 `healthy`；`inferred_used` 只作为诊断指标展示。

在线 proposal、heuristic 和 LLM candidate 会进入统一候选池。候选只用 mutate-dev 选优，而且 current active 与 candidate 必须比较同一批 dev 样本；最优候选随后进入 promotion-test，要求零硬失败、规则通过率达标，并逐 `sample_id + rule_id` 计算 RegR。默认回归率为零且不能出现硬规则回归，之后再与历史 champion 比较。完整 outputs、judgments、regression details 和 promotion reason 都会落盘。

### Q3：怎么避免沉淀垃圾 Skill？

有五层控制。第一，Attributor 先隔离 capability limit 和 evaluation noise。第二，Extractor 只抽取用户明确给出的可复用规则。第三，Maintainer 做 exact identity、相似检索和 add / merge / discard。第四，候选先进入 proposal 隔离区，不污染 active。第五，评测候选必须通过 promotion-test 质量、同样本回归和 champion gate，最后显式发布；usage tracking 另行区分 retrieved、surfaced、invoked 和 inferred_used。

评测层还有一层保护：proposal 不会因为来自 `skill_gap` 就默认正确，必须有 replay 样本、promotion-test 样本、规则通过率和回归指标支撑。candidate variants 和 champion 都不会自动覆盖 active `SKILL.md`，避免模型把一次失败样本直接改成线上能力。

### Q4：Memory 和 Skills 的区别是什么？

Memory 主要承载会话状态、任务进度和可折叠的上下文，例如当前做到哪一步、哪些工具试过、下一步怎么接；Skills 记方法和流程，例如代码审查要先列风险、政府报告要使用正式语体和固定结构。简单说，Memory 解决“长任务怎么不断档”，Skills 解决“同类任务怎么复用方法”。

### Q5：怎么保证 Agent 不乱改文件？

首先有 Plan Mode，大范围任务可以只读探索并写计划。其次工具层有统一 `check_permission()`，危险 Shell、新建文件、Skill 创建/演化会确认。再次，编辑已有文件前必须先 `read_file`，并记录 mtime；如果文件在读取后被外部修改，会要求重新读取。

### Q6：MCP 在项目里起什么作用？

MCP 用来把外部工具接入 Agent。Bear Code 自己实现了 stdio JSON-RPC MCP Client，会读取 `.mcp.json` 或 settings，启动 MCP Server，执行 initialize 和 tools/list，把外部工具包装成 `mcp__server__tool`，模型调用时再路由到对应 server 的 tools/call。

### Q7：为什么要支持子 Agent？

子 Agent 用来隔离上下文和任务范围。比如 explore 只读搜索代码，plan 只读输出方案，general 可以处理局部任务。这样主 Agent 不需要承载所有搜索细节，复杂任务也能拆分成更小的独立上下文。

### Q8：项目最大的技术难点是什么？

难点不是调用模型 API，而是把模型、工具、权限、上下文、长期记忆和自进化沉淀串成稳定闭环。尤其是自进化部分，既要能自动沉淀用户反馈，又不能让模型无约束修改自己的能力，所以需要 pending window、Extractor、Maintainer、权限控制、版本快照和 provenance 审计。

- 自研 stdio JSON-RPC MCP Client，支持 MCP Server 发现、工具包装和调用路由。
- 支持 explore / plan / general 子 Agent 和自定义 Agent，用隔离上下文处理代码探索、方案规划和局部任务。
