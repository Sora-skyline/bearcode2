# Bear Code 学习笔记：Skills 自进化与上下文压缩

本文记录阅读 Bear Code 源码时，围绕 Skills 自进化、三层 Session Memory 折叠和多级压缩流水线产生的疑问与结论。重点不是罗列函数，而是解释数据在各模块之间如何流动、哪些概念容易混淆，以及当前实现的边界。

## 1. 先建立三个核心认识

### 1.1 Skill、长期 Memory、Session Memory 不是一回事

| 类型 | 保存什么 | 生命周期 | 主要代码 |
| --- | --- | --- | --- |
| Skill | 可复用方法、流程、输出策略 | 可跨会话、可项目共享或用户共享 | `agents/skills.py`、`agents/*skill_evolution.py` |
| 长期 Memory | 项目事实、用户偏好、历史决策 | 可跨会话召回 | `agents/memory.py` |
| 折叠 Session Memory | 当前任务进度、当前目标、工具经验 | 主要服务当前长会话续跑 | `agents/session_memory.py`、`agents/agent.py` |

Skill 回答“这类事情以后应该怎么做”，长期 Memory 回答“以前发生过什么”，折叠 Session Memory 回答“这个长任务现在进行到哪里”。

### 1.2 三层记忆折叠和多级压缩流水线不是一回事

```text
三层记忆折叠
  = episode_memory + working_memory + tool_memory
  = 调用模型生成结构化状态，并替换原始消息历史

多级压缩流水线
  = 工具结果预算压缩 + 旧结果修剪 + 空闲微压缩
  = 直接缩短已有工具结果，不生成三层记忆
```

### 1.3 检索到 Skill 不等于调用了 Skill

```text
retrieved
  = 检索器认为某个 Skill 可能相关

surfaced
  = Skill 摘要已实际注入本轮模型上下文

invoked
  = Runtime 已成功找到并展开完整 Skill

inferred_used
  = 裁判模型认为最终回答体现了该 Skill 的独特工作流
```

这四个信号分别记录。只有 invoked 是确定性使用证据。

## 2. 第一轮模型实际能看到什么

新会话第一轮没有上一轮 user/assistant 历史，但模型不是只收到裸 `request`。

OpenAI-compatible 请求大致为：

```python
messages = [
    {"role": "system", "content": system_prompt},
    {"role": "user", "content": request_with_optional_skill_summary},
]
tools = [...]
```

Anthropic-compatible 请求大致为：

```python
system = system_prompt
messages = [
    {"role": "user", "content": request_with_optional_skill_summary},
]
tools = [...]
```

因此第一轮具有：

- System Prompt。
- 当前用户请求。
- 工具 schema。
- System Prompt 中的可用 Skill 清单。
- 如果检索命中，当前请求末尾还会附加 `<retrieved_skills>` 摘要。

第一轮没有上一轮 pending Skill window，所以不会立即进行基于下一轮反馈的 Skill 演化。

## 3. Skill 如何进入模型

Skill 信息分三层进入模型，以避免每次请求都装入所有完整 `SKILL.md`。

### 3.1 System Prompt 中的轻量清单

`agents/prompt.py::build_system_prompt()` 调用：

```python
agents.skills.build_skill_descriptions()
```

写入的主要是：

- Skill 名称。
- description。
- when-to-use。
- 是否可由用户通过 `/<name>` 调用。

这里不会写入完整 Skill 正文。

### 3.2 当前请求的相关 Skill 摘要

`Agent.chat()` 调用：

```text
_augment_user_message_with_skill_context()
  -> format_retrieved_skill_context()
  -> retrieve_relevant_skills()
```

最多检索三个候选，并将摘要附加到用户消息：

```text
用户原始请求

<retrieved_skills>
1. skill-name (score=0.820, source=project): description
   When to use: ...
</retrieved_skills>
```

`all_hits` 对象本身不发送给模型。Runtime 将 retrieved、surfaced 和 invoked 冻结为本轮
`skill_trace`，用于后台统计、下一轮反馈关联和 provenance。

### 3.3 完整 `SKILL.md` 通过 tool call 加载

模型判断某个 Skill 确实适用后，返回：

```json
{
  "name": "skill",
  "arguments": {
    "skill_name": "example-skill",
    "args": "当前任务参数"
  }
}
```

执行链：

```text
Agent._execute_tool_call("skill", ...)
  -> Agent._execute_skill_tool()
  -> skills.execute_skill()
  -> get_skill_by_name()
  -> resolve_skill_prompt()
```

`resolve_skill_prompt()` 会展开：

```text
$ARGUMENTS / ${ARGUMENTS}
${CLAUDE_SKILL_DIR}
```

#### Inline Skill

完整 Skill 正文作为 `tool_result` 或 `role=tool` 返回主模型。主模型在下一次 API 请求中看到正文，然后继续执行。

#### Fork Skill

完整 Skill 正文成为子 Agent 的 `custom_system_prompt`，`allowed-tools` 限制子 Agent 工具范围，主模型最终只接收子 Agent 的执行结果。

#### CLI 斜杠调用例外

用户输入 `/<skill-name>` 时：

- inline Skill 由 CLI 直接展开成一次 Agent 输入，不需要主模型先调用 `skill` 工具。
- fork Skill 仍需要进入 `skill` tool call 路径，以便 Runtime 创建隔离子 Agent。

## 4. `retrieve_relevant_skills()` 为什么会在两个地方出现

`retrieve_relevant_skills()` 是 Skill 系统共用的相关性召回器，不只服务用户请求。

| 场景 | query | limit | min_score | 目的 |
| --- | --- | ---: | ---: | --- |
| 正常请求 | 用户原始请求 | 3 | 0.08 | 提示模型当前可能适用的 Skill |
| 自进化维护 | 候选的名称、描述、触发条件、正文、tags | 8 | 0.03 | 找到可能重复的已有 Skill |

检索算法使用 BM25-lite：

- 对英文做基础词元归一化。
- 对中文补充二元切分。
- Skill 元数据重复三次，提高 name、description、when-to-use 权重。
- 正文只取前一部分，避免大型 `SKILL.md` 主导得分。
- query 直接包含 Skill 名称时给予名称加分。

它只负责召回，不负责：

- 加载完整 Skill。
- 调用 Skill。
- 决定 add 或 merge。
- 修改磁盘。

### 4.1 检索的完整链路

#### 第一步：建立候选 Skill 库

`discover_skills()` 会扫描两类目录：

- 用户级：`~/.bear/skills/<name>/SKILL.md`。
- 项目级：`<cwd>/.bear/skills/<name>/SKILL.md`。

同名 Skill 以用户级定义为准。解析结果会缓存在 `_cached_skills` 中，避免每轮请求都重新扫描磁盘。每个 `SKILL.md` 最终转换成 `SkillDefinition`，检索主要使用其 `name`、`description`、`when_to_use` 和 `prompt_template`。

#### 第二步：对用户请求分词

`retrieve_relevant_skills(query)` 首先通过 `_token_list()` 对 query 做轻量词法归一化：

- 转换为小写，并将 `_` 和 `-` 替换为空格。
- 英文和数字按连续字符串切分。
- 对以 `s` 结尾且长度大于 3 的英文词补充一个去掉 `s` 的词元，例如 `skills` 同时产生 `skills` 和 `skill`。
- 对中文补充滑动二元切分，例如“代码审查”会得到“代码”、“码审”、“审查”。
- 过滤“帮我”、“一下”、“使用”等低信息量停用词。

中文使用二元切分可以在不引入 jieba 等分词依赖的前提下增加局部模糊匹配能力，但也会产生一些无语义的二元组合。

#### 第三步：构造加权检索文档

每个 Skill 的检索词元由两部分组成：

```python
meta_terms = tokenize(name + description + when_to_use)
body_terms = tokenize(prompt_template[:2500])
terms = meta_terms * 3 + body_terms
```

名称、描述和触发条件是更高质量的匹配信号，因此通过重复三次提高权重。正文只使用前 2500 个字符，以控制检索成本，同时避免过长的 `SKILL.md` 稀释元数据的影响。

#### 第四步：使用 BM25 风格公式计分

系统先统计每个词元出现在多少个 Skill 中，然后仅对与 query 存在词元交集的 Skill 计分：

```text
idf(t) = log(1 + (N - df(t) + 0.5) / (df(t) + 0.5))

score(t, d) = idf(t) * tf(t, d) * (k1 + 1)
              / (tf(t, d) + k1 * (1 - b + b * |d| / avgdl))
```

其中 `k1 = 1.4`、`b = 0.75`。这个得分同时考虑：

- `TF`：查询词在 Skill 中出现越多，相关性越高，但边际收益递减。
- `IDF`：出现在较少 Skill 中的稀有词区分度更高。
- 文档长度归一化：避免正文很长的 Skill 因为词多而天然占优。

#### 第五步：名称加分、归一化和 Top-K

如果用户请求中直接包含完整 Skill 名称，系统会额外加 `0.15`：

```python
name_bonus = 0.15 if skill.name.lower() in query.lower() else 0.0
score = min(1.0, raw_score / max(3.0, len(query_tokens)) + name_bonus)
```

最终得分被限制在 `1.0` 以内。正常请求会过滤掉得分低于 `0.08` 的 Skill，按得分降序排列并返回前 3 个。

#### 第六步：只注入摘要，由模型做第二阶段决策

`format_retrieved_skill_context()` 不会注入完整 Skill 正文，而是把命中项格式化为：

```xml
<retrieved_skills>
1. skill-name (score=0.820, source=project): description
   When to use: ...
</retrieved_skills>
```

Runtime 把这个片段追加到当前用户请求。模型再根据用户的真实意图判断是否调用 Skill。因此整体是一个“词面召回 + LLM 判断”的两阶段架构：

```text
用户请求
  -> BM25-lite 召回最多 3 个 Skill
  -> 注入名称、描述和触发条件
  -> 模型判断是否真正匹配
  -> 调用 skill 工具
  -> 展开完整 prompt 并执行
```

需要强调：**retrieved 不等于 surfaced，surfaced 不等于 invoked，inferred_used 也不等于 invoked**。检索只生成候选，不应直接触发 Skill 执行。

#### 完整示例：检索代码审查 Skill

假设当前 Skill 库中有三个 Skill：

| Skill | description | when_to_use | 正文中的关键内容 |
| --- | --- | --- | --- |
| `code-review` | 审查 Python 代码，发现缺陷和安全风险 | 用户要求检查 PR 或代码质量 | SQL 注入、权限、异常处理等审查步骤 |
| `test-generator` | 为 Python 代码生成单元测试 | 用户要求补测试 | pytest、mock、边界条件 |
| `deploy-helper` | 辅助部署应用 | 用户要求发布或回滚 | Docker、健康检查、回滚流程 |

现在用户请求是：

```text
请使用 code-review 检查这个 Python PR 的安全问题
```

**1. Query 词项化**

`_token_list()` 会将 `code-review` 按连字符分成 `code` 和 `review`，英文转成小写，中文补充二元词元，并过滤“使用”、“这个”、“问题”等停用词。忽略中文切分产生的少量噪声后，核心查询词可以理解为：

```text
{code, review, 检查, python, pr, 安全, ...}
```

计分时 query 会转成 `set`，因此同一查询词重复出现不会让得分翻倍。

**2. 构造 Skill 文档**

`code-review` 的 `name + description + when_to_use` 被分词后重复三次，再与正文词元合并：

```text
[code, review, python, 审查, 安全, pr, ...] * 3
+ [sql, 注入, 权限, 异常, 处理, ...]
```

因此 query 中的 `code`、`review`、`python`、`pr` 和“安全”能与该 Skill 形成较多交集。注意，当前实现是词面检索，“检查”和“审查”并不会因为语义相近而自动匹配；本例中的其他共享词元仍足以完成召回。

**3. BM25-lite 排序**

- `code-review` 命中多个查询词，而且多个词位于重复三次的元数据中，得分最高。
- `test-generator` 可能只命中 `python`，因此有一定得分，但明显较低。
- `deploy-helper` 几乎没有交集，会直接被跳过或因低于阈值而被过滤。

用户原始请求还直接包含完整名称 `code-review`，所以它会再获得 `0.15` 的 `name_bonus`。如果用户只说“检查这个 Python PR 的安全问题”，则没有名称加分，但仍然可以依靠其他重叠词元召回 `code-review`。

为了便于理解，排序结果可以示意为：

| 排名 | Skill | 命中情况 | 示意得分 |
| ---: | --- | --- | ---: |
| 1 | `code-review` | 命中名称、Python、PR、安全等，并有名称加分 | 0.78 |
| 2 | `test-generator` | 主要命中 Python | 0.12 |
| - | `deploy-helper` | 无有效交集或低于阈值 | 不返回 |

> 表中得分只用于说明相对排名，不是固定计算结果。真实分数取决于 Skill 总数、词元的文档频率、每个 Skill 的长度和实际词频。

**4. 注入候选摘要**

`format_retrieved_skill_context()` 把过阈值的 Top hits 格式化后，追加到原始用户请求后面：

```xml
请使用 code-review 检查这个 Python PR 的安全问题

<retrieved_skills>
1. code-review (score=0.780, source=project): 审查 Python 代码，发现缺陷和安全风险
   When to use: 用户要求检查 PR 或代码质量
2. test-generator (score=0.120, source=project): 为 Python 代码生成单元测试
   When to use: 用户要求补测试
</retrieved_skills>
```

此时完整 `SKILL.md` 正文仍未加载到模型上下文，模型只看到候选的名称、描述和触发条件。

**5. LLM 做最终决策**

模型判断 `code-review` 与用户意图直接匹配，才调用 `skill` 工具。`execute_skill()` 随后加载完整 prompt 并展开参数，Runtime 再根据 `context` 选择 inline 或 fork。`test-generator` 虽然被 retrieved，但与“审查安全问题”不直接相关，因此模型可以忽略它。

这个例子对应的核心分层是：

```text
BM25-lite：尽快找到可能相关的 code-review
LLM       ：判断 code-review 是否真的适用
Runtime   ：加载完整 Skill，并按 inline/fork 执行
```

### 4.2 面试简答版

> 我们没有把所有 Skill 正文全量塞入上下文，而是先做一次轻量 BM25 召回。系统对用户请求以及 Skill 的名称、描述、触发条件和正文进行词项化，中文采用二元切分，英文做小写和简单复数归一化。Skill 元数据重复三次以提高权重，正文截断到 2500 字符。之后使用带 TF、IDF 和文档长度归一化的 BM25 风格公式打分，对直接出现 Skill 名称的请求再加 0.15，过滤低分结果并返回 Top 3。召回结果只注入摘要，最终是否调用仍由模型根据用户意图决定，从而兼顾上下文成本、召回率和误调用控制。

### 4.3 局限与可优化方向

当前实现的优点是简单、快速、无外部依赖且可解释，但也存在以下局限：

- 只能词面匹配，不容易识别“排查线上变慢”和“性能诊断”这样的语义近义。
- 英文归一化只简单去掉结尾 `s`，不是真正的词干提取。
- 中文二元切分可能产生噪声。
- query 词元最终转换成 `set`，因此没有利用查询端词频。
- `0.08` 阈值和得分归一化是经验性规则，需要通过真实数据校准。
- 元数据重复三次会同时增加词频和文档长度，并不是严格的字段权重模型。

可以进一步升级为：

- BM25 与 embedding 的混合召回。
- 对 `name`、`when_to_use` 和正文分字段计分，而不是直接重复词元。
- 用 LLM 或 cross-encoder 对初次召回结果重排。
- 基于 `retrieved` / `surfaced` / `relevant` / `invoked` 数据评估召回质量和误调用率。

## 5. Skill 自进化为什么要跨两轮

自进化不在当前回答结束后立刻学习，而是等待下一条用户消息验证上一轮结果。

```text
第 N 轮
用户任务 -> assistant 回答
  -> 保存 pending window

第 N+1 轮开始
  -> 取出第 N 轮 pending window
  -> 把第 N+1 轮用户消息作为上一轮结果反馈加入窗口

第 N+1 轮主回答结束
  -> 后台演化已补齐反馈的第 N 轮窗口
  -> 保存第 N+1 轮为新的 pending window
```

这样做是为了避免只凭 assistant 自己的输出，就把未经用户验证的方法沉淀成长期能力。

pending window 主要包含：

- 最近的 user/assistant 对话。
- 上一轮原始请求。
- 上一轮最终回答。
- 上一轮最高分 Skill 的紧凑引用。
- session id。

Runtime 注入的 `<retrieved_skills>` 会在构造学习证据时移除，避免系统自己的提示被误当成用户反馈。

## 6. Skill 自进化四个文件分别做什么

### 6.1 `agents/skills.py`：运行时使用层

主要职责：

- 定义 `SkillDefinition`。
- 扫描和缓存用户级、项目级 Skill。
- 解析 `SKILL.md`。
- 构建 System Prompt 的 Skill 清单。
- 根据 query 检索相关 Skill。
- 展开并执行 Skill。
- 为 create、evolve、统计和 provenance 提供统一业务入口。

心智模型：

```text
skills.py = Agent 使用 Skill 的公共 API
```

### 6.2 `agents/online_skill_evolution.py`：在线决策层

主要职责：

- `extract_online_skill_candidate()`：从跨轮反馈窗口提取最多一个候选。
- `maintain_online_skill_candidate()`：决定 add、merge 或 discard。
- `online_ingest()`：编排抽取、维护、权限和 provenance。
- `judge_retrieved_skill_adoption()`：判断 retrieved Skill 是否 relevant/inferred_used。

心智模型：

```text
online_skill_evolution.py = 决定学什么、怎么维护 Skill 集合
```

### 6.3 `agents/skill_evolution.py`：持久化和审计层

主要职责：

- 创建 `SKILL.md`。
- merge 前保存完整旧版本。
- 提升 patch 版本号。
- 写入 usage、feedback、provenance。
- 累计 retrieved/surfaced/invoked/inferred_used。
- 归档长期无效 Skill。

它不调用 LLM 判断“应该学什么”，只执行上层已经做出的决定。

心智模型：

```text
skill_evolution.py = Skill 文件仓库、版本系统和审计日志层
```

### 6.4 `agents/online_skill_eval.py`：质量评测层

主要职责：

- 从真实 provenance 构建 replay 数据集。
- 稳定划分 dev/test。
- 从 Skill 文本编译程序规则。
- 可选使用 LLM judge。
- 生成 heuristic/LLM candidate。
- 在相同任务上比较 current 与 candidate。
- 保存 run 和 champion 评测产物。

champion 不会自动覆盖 active `SKILL.md`，避免一次评测偷偷改变线上能力。

心智模型：

```text
online_skill_eval.py = Skill 的回归测试和候选版本验收系统
```

### 6.5 为什么不合并成一个文件

分层的原因：

1. 高频运行时检索必须轻量，不能携带完整评测流水线。
2. LLM 的不确定决策应与确定性的文件写入隔离。
3. 持久化可以单独测试，不需要启动模型。
4. 评测只能产出观察和 champion，不能直接越权修改 active Skill。
5. Agent 只依赖 `skills.py` 门面，不必知道底层文件布局。

完整协作关系：

```text
正常使用：
agent.py -> skills.py

在线自进化：
agent.py -> online_skill_evolution.py
         -> skills.py
         -> skill_evolution.py

质量评测：
main.py -> online_skill_eval.py
        -> 读取 active Skills、provenance、stats
        -> 保存 eval/champion，不覆盖 active Skill
```

## 7. Extractor 的四个参数

```python
extract_online_skill_candidate(
    messages=messages,
    side_query=side_query,
    skill_trace=skill_trace,
    hint=hint,
)
```

### `messages`

真实对话证据，通常是：

```python
[
    {"role": "user", "content": "上一轮任务"},
    {"role": "assistant", "content": "上一轮回答"},
    {"role": "user", "content": "下一轮反馈"},
]
```

### `side_query`

一个与主历史隔离的异步模型调用：

```python
async def side_query(system_prompt, user_message) -> str:
    ...
```

它使用当前模型，但不会把 Extractor 对话写入主 Agent 消息历史。

### `skill_trace`

上一轮的 Skill 证据轨迹，分别保存 retrieved、surfaced 和 invoked。它只提供身份上下文，不能替代真实用户证据。

### `hint`

人工抽取提示。后台自动路径通常为空，`/extract_now [hint]` 可以传入重点关注方向。

概括：

```text
messages = 从什么证据中学
side_query = 用哪个隔离模型抽取
skill_trace = 上一轮检索、展示和真实调用了哪些 Skill
hint = 人工希望重点关注什么
```

## 8. `skill_trace` 如何参与 merge 判断

单纯 retrieved/surfaced 只用于审计；invoked 是强身份引用。

Maintainer 同时使用四种信号：

1. LLM 对 candidate、skill trace、similar skills、existing skills 的语义判断。
2. `_exact_identity_match()` 对 name、description、when-to-use 的规范化精确匹配。
3. `retrieve_relevant_skills()` 对候选和已有 Skill 的相似检索。
4. 唯一 invoked Skill 或经过阈值验证的候选相似检索作为缺失 merge 目标的 fallback。

决策优先级：

```text
存在 exact_target
  -> 强制 merge 到 exact_target

LLM 建议 add，但最高相似分 >= 0.55
  -> 改为 merge 到最高分 Skill

LLM 建议 merge，但 target_skill 为空
  -> 唯一 invoked Skill
  -> 否则重新检索候选，相似分 >= 0.55 才 merge
  -> 仍不能确定则 discard

action 非 add/merge/discard
  -> 安全降级为 discard
```

因此：

```text
retrieved/surfaced 不能决定 merge 目标；唯一 invoked Skill 才能作为强 fallback。
```

当前 relevant/inferred_used 仍是弱语义判断，不会覆盖真实 invocation 证据。

## 9. Maintainer 的完整 add/merge/discard 逻辑

`maintain_online_skill_candidate()` 的流程：

```text
加载现有 Skills
  -> 精确身份匹配
  -> 召回最多 8 个相似 Skill
  -> 把 candidate/skill_trace/similar/existing 交给 LLM
  -> 解析 add/merge/discard
  -> 用确定性规则纠偏
  -> add/merge 写入隔离 proposal
  -> /skill-eval 通过质量与双锚点门禁
  -> /skill-promote 显式 create_skill() 或 evolve_skill()
```

### `discard`

候选重复、没有长期增量或 LLM 输出非法时，不生成 proposal。它是正常结果，不是系统错误。

### `merge`

Maintainer 先构造包含原 Skill 与稳定增量的完整 snapshot，再调用：

```python
skill_evolution.stage_skill_proposal(requested_action="merge")
```

proposal 不会被 `discover_skills()` 加载。只有评测成为 champion 并显式发布后，才调用 `skills.evolve_skill()`；此时持久化层会：

- 保存修改前完整快照。
- patch 版本加一。
- 更新 description、when-to-use 和 tags。
- 写入新正文并追加 Evolution Notes。
- 记录 evolve 事件。

重要边界：如果 Maintainer 没有返回 `merged_instructions`，代码会确定性保留旧正文，并把 `candidate.instructions` 追加到 proposal 的 `Proposed Addition`。active 正文仍保持不变。

### `add`

add proposal 中的新 Skill 默认：

```text
context = inline
user-invocable = false
status = pending
target = project
```

未来发布到项目级还是用户级由 `BEAR_AUTO_SKILL_TARGET` 控制。

### 发布边界

- 后台在线演化和 `/extract_now`：只生成 proposal。
- `/skill-eval`：只更新 evaluated / champion 状态与评测产物。
- `/skill-promote <skill>`：用户显式发布后 active 才改变。
- `/skill-create`、`/skill-evolve`：仍是显式直接维护入口。
- `plan`：跳过在线演化和 usage 统计写入。

## 10. usage tracking 怎么判断 Skill 是否有用

主回答结束后，`Agent._run_skill_usage_tracking()` 使用隔离 side query，将以下内容交给裁判模型：

- 原始用户请求。
- 最终 assistant 回答。
- 本轮 retrieved Skill 摘要。

裁判输出：

```json
{
  "name": "skill-name",
  "relevant": true,
  "inferred_used": false,
  "reason": "Skill 适合任务，但回答没有体现它的特有流程"
}
```

需要注意：

- `relevant`、`inferred_used` 是裁判 LLM 的语义推断。
- `invoked` 由 Runtime 在完整 Skill 成功展开时确定，并写入 `usage.jsonl`。
- 裁判漏项、解析失败或没有 side query 时，relevant/inferred_used 都保守记为 False。

累计统计保存到：

```text
.bear/skill-evolution/skill_usage_stats.json
```

默认一个用户级 Skill 的摘要 surfaced 至少 40 次且 invoked 仍不超过 0 次，会被移动到：

```text
.bear/skill-evolution/pruned/
```

项目级 Skill 默认不自动归档，除非开启 `BEAR_SKILL_PRUNE_PROJECT`。
样本与调用阈值分别由 `BEAR_SKILL_USAGE_PRUNE_MIN_SURFACED` 和
`BEAR_SKILL_USAGE_PRUNE_MAX_INVOKED` 调整。

## 11. 三层 Session Memory 代码在哪里

三层 schema 定义在：

```text
agents/session_memory.py::FOLD_SESSION_MEMORY_SYSTEM
```

### Episode Memory

```text
task_description
key_events
current_progress
```

保存任务整体意图、关键事件、结果和当前总进度。

### Working Memory

```text
immediate_goal
current_challenges
next_actions
```

保存当前子目标、阻塞点和下一步操作。

### Tool Memory

```text
tools_used
  -> tool_name
  -> effective_parameters
  -> common_errors
  -> response_pattern
  -> experience
derived_rules
```

保存本次任务中有效的工具参数、错误模式和避免重复失败的经验。

它们是当前 Session 的结构化续跑状态，不是长期 Memory，也不会自动在未来所有新会话中召回。

## 12. 三层折叠如何执行

主入口：

```text
Agent._compact_conversation()
```

执行流程：

```text
OpenAI/Anthropic 消息历史
  -> build_openai_transcript() / build_anthropic_transcript()
  -> 统一成带工具语义的 transcript
  -> side query(max_tokens=6000)
  -> FOLD_SESSION_MEMORY_SYSTEM
  -> parse_folded_memory()
  -> 保存折叠审计记录
  -> 用 <session-folded-memory> 替换原始历史
```

为了控制折叠请求本身的大小：

```python
MAX_TRANSCRIPT_CHARS = 80_000
MAX_BLOCK_CHARS = 12_000
```

单个块和完整 transcript 都会采用首尾保留方式截断。

如果 side query 失败或 JSON 无法解析：

```python
fallback_folded_memory(transcript)
```

会把截断 transcript 放入最小可继续状态，避免主任务因折叠失败直接中断。

### OpenAI 折叠后

```python
messages = [
    system_msg,
    {"role": "user", "content": folded_memory},
]
```

### Anthropic 折叠后

```python
messages = [
    {"role": "user", "content": folded_memory},
]
```

Anthropic 的 system 本来就是独立请求参数，因此不用保存在消息列表中。

## 13. 三层折叠什么时候触发

### 用户手动 `/compact`

```text
/compact
  -> Agent.compact()
  -> _compact_conversation(trigger="manual")
```

消息历史少于四条时不会折叠。

### 模型调用 `compact_context`

模型可以在以下情况主动调用：

- 上下文变长。
- 同一工具反复调用但没有进展。
- 工具连续失败。
- 工具结果噪声过多。
- 策略需要重置。

Runtime 会在 System Prompt 中动态告诉模型：

- 当前上下文利用率。
- 连续工具失败次数。
- 相同工具重复次数。
- 距离上次折叠的时间。

折叠后 `_context_cleared=True`，Runtime 会停止执行基于旧历史生成的剩余工具调用，并让模型基于折叠状态重新规划。

### Token 达到阈值自动触发

```python
effective_window = model_context_window - 20_000

if last_input_token_count > effective_window * 0.70:
    compact(trigger="auto")
```

例如200K模型：

```text
effective_window = 180K
自动折叠阈值 = 126K input tokens
```

自动检查发生在每批工具结果回写之后，因此主要保护长时间、多工具调用的 Agent 任务。

## 14. 多级压缩流水线

每次模型 API 请求之前都会执行：

```python
Agent._run_compression_pipeline()
```

执行顺序：

```text
预算压缩
  -> 旧工具结果修剪
  -> 空闲微压缩
```

### 第一级：工具结果预算压缩

上下文利用率低于50%时不处理。

```text
50%～70%：单个工具结果最多约 30,000 字符
超过 70%：单个工具结果最多约 15,000 字符
```

结果采用首尾保留，中间插入截断提示。

### 第二级：旧工具结果修剪

上下文利用率达到60%：

```python
SNIP_THRESHOLD = 0.60
KEEP_RECENT_RESULTS = 3
```

旧结果被替换为：

```text
[Content snipped - re-read if needed]
```

Anthropic 路径会根据 tool_use id 识别可修剪工具，并优先清理同一文件的旧读取结果；OpenAI 路径直接处理较早的 `role=tool` 消息。两条协议的具体修剪粒度并不完全相同。

### 第三级：空闲微压缩

距离上次模型 API 调用超过5分钟：

```python
MICROCOMPACT_IDLE_S = 5 * 60
```

只保留最近三个工具结果，旧内容替换为：

```text
[Old result cleared]
```

### 大工具结果的前置持久化

这不属于 `_run_compression_pipeline()` 三步本身，但属于同一上下文治理体系：

```python
Agent._persist_large_result()
```

工具结果超过30KB时，完整内容写入：

```text
~/.bear-code/tool-results/
```

消息历史只保留文件路径和前200行预览。

## 15. 三层折叠和多级压缩如何配合

```text
工具返回大结果
  -> 超过 30KB：完整结果落盘，只留预览

下一次模型请求前
  -> 50%：缩短单个长工具结果
  -> 60%：修剪较旧工具结果
  -> 空闲 5 分钟：清理旧工具结果

每批工具执行完成后
  -> 超过有效窗口 70%：生成三层 Session Memory，替换历史

模型也可以提前调用 compact_context
用户也可以主动执行 /compact
```

设计意图是渐进式处理：先清理局部噪声，仍然过长时才进行语义级的结构化折叠。

## 16. 折叠记录保存在哪里

结构化折叠记录保存到项目目录：

```text
.bear/sessions/<session-id>.folded-memory.jsonl
.bear/sessions/<session-id>.folded-memory.latest.json
```

- JSONL 保存每一次折叠记录。
- latest JSON 保存最近一次折叠结果。
- 每条记录包含 `trigger=manual|tool|auto`。

完整可恢复会话则保存在：

```text
~/.bear-code/sessions/<session-id>.json
```

两者用途不同：

- 完整 session 快照用于 `--resume`。
- 项目内 folded memory 用于折叠审计和观察当前任务状态。
- folded memory 不是完整对话备份，不能单独还原所有历史细节。

## 17. 常见疑问速查

### Q1：自动检索到 Skill 后，完整正文已经进入模型了吗？

没有。自动检索只注入摘要；模型随后调用 `skill` 工具，完整正文才以 tool result 或子 Agent System Prompt 进入执行链。

### Q2：加载 Skill 是 tool call 吗？

普通自然语言请求中是。模型返回 `skill` tool call，Runtime 本地读取并展开 `SKILL.md`，再把结果返回模型。CLI 的 inline 斜杠调用是例外。

### Q3：检索 Top 1 是否意味着一定 merge？

不是。Top 1 只用于提示和审计；缺少 merge 目标时优先使用唯一 invoked Skill，否则必须重新检索并通过阈值验证。

### Q4：`inferred_used=True` 是否证明实际调用过 Skill？

不能证明。它只是裁判推测；真实调用看 `invoked` 和 invocation 日志。

### Q5：第一轮为什么不能自进化？

第一轮没有下一轮用户反馈，只能先保存 pending window。下一条用户消息到来后，上一轮窗口才具备结果证据。

### Q6：多级压缩是否会生成 episode/working/tool memory？

不会。多级压缩只修改工具结果文本；只有结构化折叠才会生成三层 Session Memory。

### Q7：简单问答会自动触发70%折叠吗？

自动阈值检查目前位于工具结果处理之后，主要面向多工具 Agent Loop。简单回复若没有工具批次，通常不会走到该自动检查点；用户仍可使用 `/compact`，模型也可调用 `compact_context`。

### Q8：折叠后为什么要停止剩余工具调用？

剩余工具调用是模型基于旧历史提出的。历史已经被替换后继续执行可能失去业务语境，因此 Runtime 熔断当前工具队列，先让模型基于新折叠状态重新规划。

### Q9：折叠记忆是不是长期学习？

不是。它是当前任务的结构化交接状态。跨会话的项目事实和偏好由长期 Memory 管理，可复用流程由 Skills 管理。

### Q10：为什么 Skill 决策、写盘和评测要分开？

因为 LLM 决策具有不确定性，文件写入必须确定且可审计，评测又不应该直接改变线上能力。分层后可以分别测试，也能形成明确安全边界。

## 19. 最终心智模型

```text
Skills 自进化：
真实跨轮反馈
  -> Extractor 提炼候选
  -> Maintainer 控制 add/merge/discard
  -> 持久化层保存版本、来源和统计
  -> usage tracking 观察表现
  -> eval 层做 replay 和候选验收

上下文治理：
大结果先落盘
  -> 工具结果逐级瘦身
  -> 必要时生成 episode/working/tool 三层状态
  -> 用结构化状态替换旧历史
  -> Agent 从压缩后的任务交接继续执行
```

这两个系统解决的是不同问题：Skill 自进化让 Agent 在未来相似任务中做得更好；三层折叠和多级压缩让 Agent 在当前长任务中不因上下文膨胀而失去进度。
